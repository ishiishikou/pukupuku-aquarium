# 推奨仕様と評価計画

以下は採用提案。製品仕様の最終決定ではない。

## 最小の試作

現行Aquarium型のルールを維持し、水路は外す。セル単位に未確定・水・乾燥を記録する。水／乾燥のモードを常時表示し、同じ状態のセルを再タップすると未確定に戻す案を基準にする。モード切替による誤入力は、循環入力方式との比較項目にする。

水槽境界を太く、内部線を細くする。色だけに依存せず、水・×・未確定を形でも区別する。選択した水槽全体を一時強調し、完成した水位と部分入力を描き分ける。チュートリアルは「0と満数」「同じ高さ」「下方向」の順で3問、説明を閉じても解けるかを確認する。

通常入力では保存解を参照した正誤通知をしない。行列の合計超過、確定済みの水／乾燥間の物理矛盾など、公開情報から説明できる矛盾だけを任意表示する。ヒントは対象→使う規則→結論の段階表示とし、単に答えのセルを塗らない。

クリアは全マス確定と全制約の充足で判定。入力を自動で他のセルへ伝播させるかは比較実験まで固定しない。補助操作を入れる場合は、確定する範囲をプレビューし、1操作で取り消せるようにする。

## 触覚・泡・音

入力が受理された瞬間を1つのイベントとし、泡の発生、短い音、短い振動を結びつける。水は柔らかい一発、乾燥は控えめな一発、クリアだけ短い別パターンを候補とする。正解に近いほど振動を変える方式は使わない。同じ操作・同じ設定には一貫した応答を返す。

ネイティブ候補は[Apple Core Haptics](https://developer.apple.com/documentation/corehaptics)と[音・触覚の同期に関するApple解説](https://developer.apple.com/videos/play/wwdc2019/520/)。同じパターンで音と触覚を再生する設計を検討するが、画面描画まで自動的に同期されると仮定せず、入力時刻と描画・再生要求を記録して実機で評価する。

このレビューではSwift実装・Xcode SDK照合・コンパイル・実機の触覚検証は行っていない。API採用と最小OSは実装時の検証で確定する。引き継ぎ情報上、iPhoneブラウザ版では振動未対応なので、ブラウザ試遊だけで触覚の合否を判断しない。

音・振動・動きを独立に調整／無効化できるようにする。連打で重い振動が重ならないこと、無音時・低減モーション時も判断できることを確認する。生き物は盤外に配置し、入力を遮らず、勝手に盤面を変えない。

## 比較実験と採否（数値は初期の仮基準）

| 段階 | 方法 | 記録と次へ進む条件 |
| --- | --- | --- |
| 1: 理解 | 初見5人、チュートリアル後の新しい問題を介助なしで試遊 | 4人以上が水平・下方向・×と未入力の違いを説明し、最初の問題を解く。誤読箇所を記録 |
| 2: 入力 | セル入力と水位入力、必要なら一括確定を比較。別の同難度問題を使い、試す順序を入れ替える | 誤入力・取り消し・ヒント・総タップ数・推理終了後の操作時間・好みを記録。速さだけで勝者を決めない |
| 3: 触覚 | 対応iPhoneで同じ盤面操作を、振動なし／弱／標準で比較。各条件を短時間と10分間で評価 | 5段階の快さと疲労感、連打・消音・復帰時の不具合を確認。過半数が振動ありを選ぶことを暫定基準とする |
| 4: 難度 | 推測不要の30問を作り、数日に分けて評価 | 解答時間・ヒント率・離脱・手筋の分布を確認。暫定2〜5分帯を狙い、対象ユーザーの結果で帯を再設定 |

小人数の結果を統計的な市場検証とは呼ばない。初期の設計不良を見つけるために使う。検証参加者の記録は匿名化し、生の録画や個人情報をPublicリポジトリへ登録しない。

独自ルールの追加は、基本の理解と触覚評価が通ってから判断する。水路を再検討するなら、見た目の違いでなく新しい必然手順が生まれる問題を先に2〜3問作る。
