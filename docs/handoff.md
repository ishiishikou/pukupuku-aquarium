## 迷ったときの判断軸

目指すのは「ひとつ気づく→数マスをぷくぷくと埋める→次の気づきにつながる」。ほどよく考えながら、もう1問触りたくなる小さな日課。

タップ数を増やすことも減らすことも目的ではない。自分で分かったことを入力する気持ちよさを残し、分かった後に延々と埋める負担を減らす。セル入力が基準。終盤の乾燥一括完了は比較候補で、採用済みとしない。ヒントは理由を伝える。水路・動的な盤面変化・収集・日次ノルマは今の試作範囲外。

## 再開時の環境確認

GitHubから指定ブランチを直接読み、実際にコード実行・ファイル出力・ブラウザ操作ができるか確認する。検索0件だけでファイルがないと判断しない。Windowsのローカルパスや前チャットの起動サーバーを前提にしない。

コード実行ができれば既存テストを1回実行して基準を確認する。読み書きだけ可能なら成果物をGitHubへ保存し、未実行を明記する。GitHubへ書けない場合はパッチ等の成果物と適用先を用意し、書き込んだと報告しない。実機環境がなくても作問・ブラウザ試作・説明の検討は進められるが、触覚評価は別に残す。

```sh
python scripts/audit_original.py
python -m unittest discover -s scripts -p 'test_*.py'
```

検証はassertを含むため `python -O` は使わない。既存結果は8テスト成功。audit_original.pyは原版専用の抽出・再検査であり、新しい問題生成器ではない。新問は同形式JSONを作り `python scripts/verify.py 新問.json` で一意性を確認し、別に推理手順を示す。200万候補の上限到達を合格としない。小問題用の検証器を大量生成向けと誤認しない。

## 次の最小作業

Issue #3を入口に、まず本編1問分の体験を最後まで通す。新しい5問と大きなUIを一度に作り込まない。

1. 5×5を目安に「水槽の幅か水平・下方向を使う小さな気づき→数マスの入力→次の気づき」を含む代表1問を作る。
2. 正解を探索の制約に使わず一意性を検査する。具体的推理と入力区間を示す。残数だけで完結するかも調べる。人に楽しいかは未評価と記す。
3. 原版とは別の改善版へ、この1問のセル入力、領域強調、理由付きヒント、取り消し、クリア・終了までを実装する。別localStorageキーを使う。泡の見た目で未確定の答えを先に見せない。
4. 実行できる環境で動作確認し、遊べる成果物と短い評価観点をユーザーへ渡す。ここでは全体の完成や楽しさの実証を宣言しない。
5. 1問の問題点を直して導入3問＋本編5問＋任意1問へ広げる。同じセットをIssue #4のiPhone実機比較へつなぐ。30問制作はその結果を見て進める。

残数や水槽の規則が推理器で通るだけでは、気づきが自然とは限らない。最初の2問が残数だけで解ける原版の順番は、新版の導入の正解としない。原版の答え開示ヒントや案内上書きの不具合もそのまま移植しない。

## レビューで見ること

- 数学的成立、動作、初見の理解、快さを別々に報告しているか。
- 「もう1問」の選択が報酬や誘導で作られていないか。
- 水だけでなく×の入力も快いか。終盤の手数を増やして満足感と誤認していないか。
- ヒントの理由と新問の一意性に再現できる根拠があるか。
- ブラウザの泡・音をiPhoneの振動評価の代わりにしていないか。

新ルールの追加、全体自動入力への転換、問題量産、触覚の採否は設計上の節目としてユーザーに結果を示す。細かな実装選択は現行仕様の範囲で進めてよい。
