# ぷくぷく水槽 — App Store一般公開マスターロードマップ

この文書は**完成までのゲート**と責任境界を統合する。数学/ゲームデザイン/実装/配布の正本を混同しない。完成はApp Storeの一般公開と初期サポート体制の確認によって判定し、MVPやTestFlightで完了としない。2026-11-01の最新ユーザー方針を優先し、古いAstraレビューは歴史的な独立レビューとして扱う。**本ロードマップ自体はまだAstraなど別担当による完成レビューを受けていない。**

## 不変要件と更新した方針

1. **推理の面白さと安定難度**: 難しすぎず、短い「気づき→確定→次の気づき」が続く論理パズル。問題が一意でも難易度・楽しさを証明したことにはならない。ブラウザ試作はこの軸だけを評価する。
2. **iPhoneに固有の操作**: 指でなぞり、通過セルへ水/乾燥を連続反映する。短い触覚・音・泡を各受理入力へ同期させる。連打/方向転換/高速移動/同じセルへの再進入/中断/取消で不自然な入力・多重再生を起こさない。評価は実機のみ（#4）。
3. **問題供給の戦略**: 無制限に独立問題を量産しない。目安**約100の母問題**を作問・検証し、見た目（背景/スキン/生き物/水面）、出題順、安全に証明した盤面変換を組み合わせ、長く繰り返し遊べるようにする。100は検証前の概数であり固定ノルマではない。
4. **継続動機**: ユーザーの新要望として、レベルの積み上げ、毎日のプレイの実績、継続してきた価値の実感を持たせたい。**レベルは進捗でありパズル難度が単調に上がる意味ではない**。日次継続・レベル演出を設計するが、意図的な誤認/購入への誘導/過度な損失圧力にはしない。毎日やることが義務になる前提では作らず、強度は後続のユーザー試遊で確認する。
5. **一般公開**: App Storeで一般公開し、リリース後の修正・サポートができる。**Apple Developer Program登録はユーザー申告で完了済み**。再登録の依頼は不要。署名・配信可能性は現実の接続で別途確認する。

## ゲートと完了判定

### G0 技術/製品仕様の決定（AIが先行）
- SwiftUI+Core Haptics等のネイティブ方式、React Native/Expo+ネイティブモジュール等を比較。「Windows中心で開発できるか」だけでなく、署名/クラウドmacOSビルド・速度・低遅延で動くなぞりと触覚・保守性・費用を確認。
- 構成の最終選定は**実機に到達する最小vertical sliceの証拠**を優先。未知のSDK機能を使えるものと決めつけない。
- UI/進捗/問題データ/テスト・ビルド・デプロイを分離。ゲームは必要な通信を持たないローカルファーストを第一候補とし、分析・同期の追加は後で根拠と同意を確認。
- 出荷ゲート: 候補比較と採否の理由、技術的ブロッカーと最初の実機ビルド手順が記録されている。

### G1 iPhoneの必達操作の成立（Issue #4）
- 2問程度で、指のなぞりによる連続確定、速度変化・折り返し・再通過時の重複防止、ストローク単位の取り消しを動作確認する。
- 入力を受理したタイミングから触覚・音・泡を揃える。水/×/取消の短い差を試し、正誤で強弱をつけない。高速なぞりによる取りこぼし、音の多重再生、ミュート・復帰・設定OFFも確認。
- 出荷ゲート: 署名済みiPhone実機で再現可能な検証と本人の快さ評価。シミュレータ/ブラウザだけでは合格扱いしない。

### G2 問題の安定品質と反復供給（Issue #3 / #5）
- 導入3問・本編5問+任意6問目は「推理の気づき」「再度遊ぶ意欲」を観測。最初のユーザーの好反応は有望だが、独立した継続性の証明ではない。
- 数学的な正当性、一意解、保存解を参照しない推論ログ、難度帯、解法の独立性と似た問題の連続を自動検査する。
- 比較用30問を経て、目安100の母問題を品質重視で確保。**100問すべての変換後盤面に検証を実行**し、変換自体の正しさをユニットテストする。
- 左右反転は重力と水位を保つ候補。上下反転だけでは水位が下からたまる制約を壊すため不可。上下反転+水/乾燥の反転は数学的に候補だが、境界・ヒント・水の数・難度を含む独立の再検査が条件。色替え/ラベル入れ替えだけを異なる問題数と数えない。
- 母問題ごとの出題履歴・最近使った変換を保持し、近接再出題を避ける。**完全に繰り返しと気づかれない保証はない**ため、複数日テストで再認識率と退屈・心地よさを確認する。
- 出荷ゲート: 難度の安定、同じ母問題再登場の負担の小ささ、一意性/推理のテスト証拠が揃っている。数だけの大量生成はしない。

### G3 継続設計・製品完成
- ループ: 今日の一問/続きを開く → 気づく → 気持ちよくなぞる → クリア → レベルの進捗が積み上がる → 自発的に次へ。
- レベルはクリア実績の蓄積、難度は別の内部指標。デイリー実績/プレイ履歴/獲得演出・日付変更での整合/休止復帰/端末日付変更も設計する。
- ストリークの喪失や強いFOMOは**採用未確定**。失効を導入する場合はユーザーの体験評価とApp Store審査観点を別途通す。通知を入れる場合は端末許可とユーザー設定を尊重する。
- 起動/保存/途中再開/問題進捗/Undo/設定/音/触覚/動きの調整/無音・Reduced Motion/アクセシビリティ、プライバシー、利用規約等の必要性、UI/音/画像の権利、クラッシュ対応を完成させる。
- メタデータや画面で実際より大量の**独立した新問**が存在するかのように謳わない。ゲーム体験の新鮮さで勝負する。
- 出荷ゲート: 長時間/複数日使用に耐え、保存・UI・描画・音・触覚・難度・レベル実績がすべて破綻しない。

### G4 App Store審査準備
- iOSターゲット/SDK・署名/プロビジョニング/App Store Connect/TestFlightの実際の接続、申請上の権利・年齢区分・提供地域・プライバシーデータ開示・問い合わせ先・ストア素材・スクリーンショットを整備。
- 公開前の独立な実機/設計レビューを得る。旧AstraレビューをApp Store完成版レビューとして流用しない。
- Appleの[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) 2.1（完成度）、2.3（正確なメタデータ）、4.1（コピー作品）、5.2（権利）、5.6（操作的/誤認的行為）と現行のストア審査要件を公開直前に再確認。
- ユーザーは評価ビルドへのフィードバックと、App Store Connect上で本人権限が必須の操作にのみ参加。AI側の実装/検査で代替できる依頼を作らない。

### G5 公開と初期運用
- 審査提出 → 指摘対応 → Apple承認 → 公開URL/地域・検索可能性を確認 → クラッシュ・問い合わせ・更新経路を確立。
- 出荷ゲート: **一般公開が確認されていること**。審査提出しただけ、TestFlight配布しただけ、CI緑だけでは未完成。
